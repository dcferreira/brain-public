# Dispatch — Prepare and Launch a Worker

> **Harness.** If you have a `task` tool you are in omp: read `~/projects/brain/skills/_shared/harness/omp.md`. If you have an `Agent` tool you are in Claude Code: read `~/projects/brain/skills/_shared/harness/claude-code.md`. Read one, never both.

Turn a **Today** action into a primed, detached worker session you can attach to. The worker gathers its own context, proposes a concise action list, then by default behaves as a normal interactive session — it is **not** fire-and-forget. Only when the user or the dispatching manager asks for it to start autonomously (`start_autonomously: true` on the note) does it carry straight on into the work after its greeting.

**How this runs:** the *main session* does only two things — it identifies the target Today action (Step 1), and, as the sole writer of top-of-mind and private.md, performs the final status flip and one-line report (Step 3). Everything in between is delegated to a **single launcher subagent** (Step 2) that performs the whole prepare-and-launch — classify scope → gather context at the worker's scope → classify code/non-code → derive slug → resolve host and harness → preflight and verify the project directory → write the worker note → launch the detached session → verify startup → set the worker note to `working` — and returns only a concise summary. This keeps the qmd log, the worker-note body and the captured pane output out of the main thread, so the main-session context cost is essentially one line in and one line out plus the top-of-mind flip. The launcher subagent **must never touch top-of-mind or private.md**; the brain-dispatch and brain-collect skills are the only coordinators that move Today statuses, and the main session remains the sole writer of top-of-mind (except a coordinator worker's own workers' Today lines — see the priming's coordinator exception).

## Vault & path facts

- Vault: `~/Obsidian/vault`
- Top of mind: `00-home/top-of-mind.md` — **Today** actions (`[ ]`/`[/]`/`[x]`/`[-]`), **This week** goals.
- Private Today file: `private/private.md` — **Today** items marked `[private]`; only read or written when `brain-scope includes "$(brain-scope norm)" private` (see launcher step 1 in Step 2).
- Worker notes: `$(brain-scope note-dir <area> workers)/<slug>.md` — `workers/<slug>.md` for `work`/`projects`, `private/workers/<slug>.md` for `private`; create the folder on first use. To find an existing note by slug: `brain-scope find-worker <slug>`.
- Scope registries: `00-home/scopes.md` (work + projects) and `private/scopes.md` (private) — markdown tables `| project | area | aliases | slug prefixes |`.
- **Hosts.** Worker hosts are listed in `~/projects/brain/skills/_shared/hosts.conf` by real name (e.g. `desktop`, `homeserver`); `local` is only a deprecated alias for "this machine", normalised to its real name. This machine's name is resolved from its hostname by `self_host` (`lib/host.sh`). Omitted `--host` → this machine's real name; omitted `--harness` → the host's default; a pair the file does not allow is refused before anything is written.
- jj workspaces (code tasks): `~/projects/jj-workspaces/<slug>` — a dedicated dir kept out of the main checkouts, created by the **worker** (not dispatch). (Convention; adjust if needed.)
- Local repo location convention (for resolving a repo to a path): repos live at `~/projects/<repo>`, cloned from `github.com/example-user/<repo>` (e.g. `github.com/example-user/budgebell` → `~/projects/budgebell`).
- **Editing tracked vault files.** When the main session flips a Today action, it mutates top-of-mind (or private.md) through the harness `read` → `edit`/`write` flow only — **never** with shell text-rewrites (`awk`/`sed -i`/`cp`/`mv`/`>` redirection). An out-of-band write changes the file behind the harness and makes the next edit fail with a stale-read error (this stalled the planning skills on 21 Aug 2026). If an out-of-band write is ever genuinely unavoidable, `read` the file again immediately, before any further `edit`.

## Step 1 — identify the target Today action

From the argument, or by matching against the **Today** section of `00-home/top-of-mind.md` (and of `private/private.md` too when `brain-scope includes "$(brain-scope norm)" private`; items there carry the `[private]` marker). If the match is ambiguous, ask the user which action they mean. Note whether an explicit **base directory** argument was given (a bare repo name resolved via the convention above, or an absolute path) — it overrides project inference in Step 4.

**Parse the host and harness out of the argument.** `--host <name>` and `--harness omp|claude` are optional flags on the argument line; strip them from the action text before matching. Missing `--host` → this machine's real name: run `bash -c '. ~/projects/brain/skills/_shared/lib/host.sh; self_host'` and use what it prints. An explicit `--host local` is a deprecated alias — normalise it the same way. If that command prints nothing (exit 1), **stop** and tell the user to add this machine's hostname (`hostname -s`) to its `hostnames` column in `~/projects/brain/skills/_shared/hosts.conf` or to set `BRAIN_SELF_HOST`; dispatch nothing. The resolved host is always a real `hosts.conf` name — pass that (never `local`) to the launcher, and the worker note records it. Missing `--harness` → that host's `default_harness` from `hosts.conf`. Pass both to the launcher subagent in Step 2 — it refuses a disallowed pair in its preflight, before anything is written.

**Start mode and dispatcher.** `start_autonomously` is `true` only when the request (from the user or the dispatching manager) asks for the worker to run autonomously or start immediately; otherwise `false` — read it from the request, do not ask when it is clear. `dispatcher` is your own tmux session name (`tmux display-message -p '#S'` when in tmux), else `main`. Two optional inputs, read the same way and empty unless the request gives them: **`model`** (a model id to pin the worker's harness to, e.g. a coordinator asking for `claude-sonnet-5-5`) and **task-specific instructions** (text the request wants carried into the brief verbatim, e.g. a role or a standing-rules block). Pass all four to the launcher.

**Resume an existing blocked/parked worker.** Derive the slug the action would produce and check `brain-scope find-worker <slug>` (it looks in `workers/` and `private/workers/`). If a worker note already exists for it with `status: blocked` or `status: parked`, this is a **resume**, not a fresh launch: relaunch the session pointing the worker at the **existing** note (which holds its accumulated Result section and gathered context), keeping that context intact. Do **not** overwrite the note, its brief, or its gathered context. Tell the launcher subagent (Step 2) it is resuming this slug so it re-uses the note rather than writing a new one — and for a `parked` **code** task the jj workspace was deliberately kept, so the worker `cd`s back into it rather than creating a new one. A resume re-uses the note's recorded `host`, `harness` and `model` unless the user overrides them explicitly.

## Step 2 — delegate prepare-and-launch to a launcher subagent

Dispatch a **single** general-purpose subagent and give it the instructions in the blockquote below **verbatim** (substitute the action text, any explicit base-directory argument, the resolved host and harness, `start_autonomously`, `dispatcher`, and the optional model and task-specific instructions — empty when not given). It performs the **entire** prepare-and-launch and returns **only a concise summary** — the verbose qmd log, the worker-note body and the captured pane output all stay inside the subagent. It **must not** touch top-of-mind; that is the main session's job in Step 3.

> You are launching a primed, detached worker session for a **Today** action. Do the whole prepare-and-launch below and return only the concise summary specified at the end. Use the `qmd` CLI and native file tools. Do **not** touch `00-home/top-of-mind.md` or `private/private.md` — the main session owns those. The originating Today action is: **`<today action>`**. Explicit base-directory argument (may be empty): **`<base directory>`**. Host: **`<host>`**. Harness: **`<harness>`**. Start autonomously: **`<true|false>`**. Dispatcher: **`<dispatcher>`**. Model (may be empty): **`<model>`**. Task-specific instructions (may be empty), between the markers: **`<<<`**`<task-specific instructions>`**`>>>`**.
>
> **0. Resume check.** If a worker note already exists (`brain-scope find-worker <slug>` prints its path; it may be under `workers/` or `private/workers/`) for this action's slug with `status: blocked` or `status: parked`, you are **resuming**, not starting fresh: **skip step 5's note-writing** — keep the existing note, its `## Brief`, its `## Gathered context`, and its accumulated Result section **exactly as they are** (do not overwrite them). Re-use the recorded `project_dir` and the recorded `model:` (if any) as the model for step 7 — a model given in this request overrides it, and you write the override back to the note's `model:` — and for a `parked` **code** task re-use the existing `jj_workspace` (it was deliberately kept). Set `status: working` on verified relaunch. Prime the resumed session to read the existing note (including its Result section so far) and, for a parked code task, to `cd` back into the existing `jj_workspace` rather than creating a new one. Otherwise proceed with a fresh launch as below.
>
> **1. Classify scope (before gathering anything).** Pick the action's `area` (`work` | `projects` | `private`) and `project` slug. Read the registries (`00-home/scopes.md`, and `private/scopes.md` when your scope includes private) and match the action text, its aliases and the candidate slug prefix; a `[private]`-marked Today item is `private`. If it is unclear, **ask the user** — do not guess. If the project is new, append a row to the right registry (`private/scopes.md` for private, else `00-home/scopes.md`; if that registry file does not exist yet, first copy it from `~/projects/brain/bin/seed/scopes.private.md` / `scopes.shared.md`, then append) and say so in one line in your return summary. Then derive: the worker-note directory `$(brain-scope note-dir <area> workers)`, and the worker scope for the launch scripts — `--scope all` when `project` is `brain`, `--scope private` for other private work, else `--scope shared`. The **worker scope** is `shared` unless the area is `private` (then `all` for project `brain`, else `private`); step 1b gathers at that scope, never at your own.
>
> **1b. Gather context — cheaply, as pointers not prose, at the worker's scope.** The worker ground-truths everything in its premise check (step 5 priming), so your job here is **breadcrumbs, not a distilled dossier** — over-gathering just bakes in stale claims the worker must re-verify anyway, and is the single biggest source of wasted launcher effort. Spend the minimum:
> - one `brain-search --scope <worker scope> --project <slug> -n 5 "<key terms>"` (the worker scope and project slug come from step 1 — `shared` unless the area is private; always pass `--scope` explicitly, because your own `$BRAIN_SCOPE` is the coordinator's, usually `all`, and must not decide what the worker's brief can see; add an `env -u CI qmd vsearch` only if the keyword search clearly missed — `CI=true`, which a harness bash tool commonly sets, makes plain `qmd vsearch` abort) — capture note **paths**, not their bodies;
> - the **path(s)** of any directly relevant `meetings/` note (do not paste transcripts);
> - the **This week** goal (from `00-home/top-of-mind.md`, or `private/private.md` for a `[private]` action) this action serves (read-only lookup — do not edit the file);
> - your best guess at the associated **project/repo**.
>
>   Assemble these into a **thin brief**: a one-line statement of intent; the served week-goal; a short list of **pointers** (note paths, MR/ticket URLs, endpoints, IDs) the worker can follow; and the candidate project/repo. Do **not** paste note bodies, and — apart from the `project_dir`/VCS the preflight confirms in step 4 — do **not** resolve or confirm anything external here; that is the worker's premise check. **Tag every load-bearing item `[verified]` or `[lead]`** (see step 5). **Never cite `private/` paths or private content in the brief or `## Gathered context` of a `work` or `projects` worker** — drop any such hit, including from the served week-goal lookup (`private/private.md` is read only for a `[private]` action).
>
> **2. Classify the task.** **code** (touches a repo — needs a jj workspace) or **non-code** (a follow-up, a draft, a design, an analysis). Decide from the action and the brief.
>
> **3. Derive the slug.** Short kebab-case from the action (e.g. `flaky-ui-suite`, `follow-up-sam-recordings`). Shared across the worker session name, the worker-note filename, and the jj workspace name.
>
> **4. Resolve the project directory, then preflight the host.**
> - An explicit base-directory argument wins; otherwise use your inferred project, resolved via the location convention: repos live at `~/projects/<repo>` (cloned from `github.com/example-user/<repo>`). A bare repo name in the base-directory argument is resolved the same way; an absolute path is used as-is. Write paths with a leading `~` so they are valid on either host.
> - **Fall back to `~/projects/workbench`** (a plain non-repo directory, created on every host by `claude/install.sh`) only for a **non-code** worker with no associated project. A code task always has a repo; if none can be found, ask the user rather than guessing. `~/projects/brain` is used **only** for workers whose `project:` is `brain`, because the brain repo's `.claude/settings.json` forces `BRAIN_SCOPE=all` and overrides the per-worker scope (`launch-worker.sh` refuses a fresh non-`all` launch rooted there). The worker session's cwd is this project directory for **both** code and non-code — this co-locates all sessions for a project.
> - **Run the preflight before writing anything:** `bash ~/projects/brain/skills/brain-dispatch/scripts/preflight.sh --host <host> --harness <harness> --project-dir <project_dir>`. It prints one line: `dir_exists=yes|no vcs=jj|git|none free_gb=<int> harness_bin=present|missing guardrail=active|inactive|n/a`. Every probe runs **on the target host**. Interpret it:
>   - **Non-zero rc — stop, write nothing, launch nothing.** **rc 2** is bad arguments, an unknown host, an unknown harness name, or a host/harness pair `hosts.conf` does not allow; **rc 1** is `dir_exists=no` or `harness_bin=missing`. Report the refusal or failure (the resolved path that was missing, or the absent harness binary on that host) and do **not** write the worker note or launch anything.
>   - **`vcs`** — record it in the note's `vcs` field and emit the matching step 0 in the brief (`jj workspace add` for jj, `git worktree add` for git), never both and never a guess. Detecting it at brief-writing time is load-bearing: the worker's step 0 differs for jj and git, and one brief that assumed jj on a git repo burned the session on its first command. `vcs=none` for a non-code task is fine; for a code task, treat it as a failed premise and report.
>   - **`free_gb`** — a concurrent worker fleet plus build/test artefacts filled a disk to 100% twice in two days. Below **~20 GB**: launch, but **warn** in the return summary. Below **~5 GB**: **refuse to launch a `code` worker** — stop, and tell the user to reclaim space first (see the vault note *reclaim Mac disk by pruning Docker not language caches* — `docker system prune`, not language caches). A **non-code** worker may still launch below 5 GB, with the warning.
>   - **`guardrail=inactive`** — the host's tool-call guardrail is not running and the preflight could not start it. Launch, but **warn** in the return summary: the worker's tool calls stay blocked until it is reachable. `guardrail=n/a` means that host/harness pair has none, and is not a warning.
>
> **5. Write the worker note (`status: primed`).** Create `$(brain-scope note-dir <area> workers)/<slug>.md` (make the folder if absent) with this exact frontmatter and body:
>

> area: <work | projects | private>   # from step 1
> project: <project slug from the registry, or the best-fit new slug>   # from step 1

> week_goal: <the This week goal it serves>
> task_type: code | non-code
> host: <hosts.conf host name — always a real name (e.g. desktop, homeserver), never `local`>
> harness: <the resolved harness>
> attach: <tmux attach -t brain-worker-<slug> when the host is this machine; ssh -t <ssh_alias> tmux attach -t brain-worker-<slug> for another host — ssh_alias from hosts.conf>
> project_dir: <resolved project directory, on the worker host, written with `~`>
> tmux_session: brain-worker-<slug>
> vcs: jj | git   # from the step 4 preflight; drives the worker's step 0 (jj workspace vs git worktree); omit for non-code
> jj_workspace: ~/projects/jj-workspaces/<slug>   # intended path the worker will create (a git worktree for a git repo); omit for non-code
> start_autonomously: false   # true only when the dispatch request asked for it; drives the "On start" priming

> status: primed   # allowed values, ONLY these: primed | working | blocked | done | parked | collected. Lifecycle: primed → working → blocked → done → collected (plus parked). A **code** worker finishes as `blocked` (awaiting review/merge) and NEVER as `done`; only a non-code worker reaches `done`. Never invent another word.
> blocker: <what/who this worker is waiting on>   # only present when status is blocked or parked; omit otherwise
> collect_state: <collecting | persisted>   # optional; set by the brain-collect skill to `collecting`, flipped to `persisted` by the worker's scoped persist; absent normally
> ---
>
> # <slug>
>

>

>

> **Tag every `## Gathered context` item `[verified: <evidence>]` or `[lead]`.** Step 1b is deliberately thin and confirms almost nothing external, so **most items are `[lead]`** — an unconfirmed pointer for the worker to follow. Mark an item `[verified: <path:line | command output | URL>]` **only** for what you actually checked at dispatch time (in practice: the `project_dir` exists and its VCS, from step 4). The worker's premise check must confirm every `[lead]` before building on it. This is the *Subagent claim contract* (below), applied to the brief the worker inherits — so a stale snapshot can never masquerade as an established fact.
>
> **Task-specific instructions.** When the request gave any, append them to `## Brief` **verbatim** — not summarised, not merged into the priming — under a `### Task-specific instructions` heading, after the priming below. Where they conflict with the standard priming they win, except that they never relax the premise check, the claim contract or the never-merge rule.
>
> The worker note carries the priming for the launched session. Append this priming to the `## Brief` section so the worker session reads it on start:
>
> - **Searching the vault:** use `brain-search [--project <project>] "<terms>"` (the `project:` from this note's frontmatter), never raw `qmd search`; it applies your `$BRAIN_SCOPE`. A worker in shared scope does **not** read `private/` — never open anything under `private/` unless your scope is `private` or `all`.
> - **On start:** read this note, absorb the gathered context, **run the premise check below**, then greet with a **concise proposed action list** phrased as *intent* ("fix the flaky UI integration suite"), **not** step-by-step instructions. Then, by `start_autonomously` in the frontmatter:
>   - `false` (default): behave as a normal interactive session the user drives.
>   - `true`: make the greeting one line with the action list, then **keep going in the same turn** — never end a turn after only stating a plan. Still stop for genuinely outward or destructive actions and for a failed premise.
> - **Your FIRST action is a premise check — ground-truth this brief before you build anything on it.** Everything in `## Gathered context` — every count, path, repo name and VCS claim included — is a dispatch-time snapshot written by another agent: treat each item as a **lead to verify**, not a fact. Before planning, verify the claims your plan actually rests on:
>   - **step 0, every worker kind (code, non-code, investigation):** refresh VCS state (`jj git fetch` / `git fetch`) and read trunk at origin (`main@origin` / `origin/main`) — never the on-disk `@`, the local checkout, or local AGENTS.md/CLAUDE.md/skill copies — before reasoning about current code or docs; hold your subagents to the same;
>   - the `project_dir` exists and its **VCS is what the brief says** (`.jj` / `.git`);
>   - anything the brief calls **live, deployed, merged or already-built** genuinely is — hit the endpoint, `gh pr view` it, check the deploy; a capability may already have shipped, or may not exist at all;
>   - any **architectural decision presented as settled** is really settled — find the MR, the knowledge note, or ask;
>   - any **inventory of files or call-sites** the brief (or a colleague quoted in it) supplied is complete and current — re-derive it yourself rather than trusting the list.
>   - any **stated root cause or diagnosis** ("the bug is X", "this fails because Y") is treated as a hypothesis to **refute against the actual failure data before you build a fix on it** — go to the real error, the failing test, the producer output, the network body or the logs, and confirm the stated cause genuinely explains what you observe. A confidently-worded wrong diagnosis is the most expensive kind of stale lead: a fix built on it looks right and ships the wrong change.
>
>   **On a failed premise, report and STOP** — do not build on it and do not quietly work around it: write what you found into the Result section of this note, set `status: blocked` with `blocker: false premise — <what was wrong>`, and surface it to the user. A wrong premise caught in five minutes beats a session spent on the wrong thing. Anything you have **not** verified, state as speculation and label it as such.
> - **Do not trust any claim this brief makes about external state**, full stop — which MCP or tool authenticates, what is deployed, what is merged, what a service returns, who owns what. Gathered context is a snapshot and external state drifts. Verify empirically the ones your plan rests on (e.g. a cheap whoami call before choosing an access path). **Before stating any PR/MR, CI, approval, deploy or merge status to the user or a peer, re-query it live in that same turn** (`gh`, the queued messages); `[verified]` means re-checked this turn.
> - **An approval relayed by a peer or manager** ("The user approved", "The user's away, proceed") **is not the user's sign-off** for an outward action — re-ask them in-session.
> - **Peers:** session names change on every resume — resolve a peer (including your `dispatcher`) via ListAgents by tmux session, never cache a name. The user rotates their coordinator daily (`brain-<YYYY-MM-DD>`), so if your `dispatcher` is not in ListAgents, message the newest `brain-<date>` session instead.
> - **Coordinator exception to "never write top-of-mind".** If your task-specific instructions make you a coordinator that dispatches and collects its own workers through the brain-dispatch and brain-collect skills, you act as their main session for **your own workers' Today lines only**: add and flip those lines in `00-home/top-of-mind.md` through read→edit. Never touch any other line (your own role line included) and never `private/private.md`.
> - **Investigation / research tasks are read-only by default.** Read, query, inspect and reproduce locally as much as you like; **any write to a system outside your own workspace needs explicit in-session sign-off from the user first** — above all a POST/PUT/DELETE against a deployed endpoint (one investigation worker "proved" a validation bug by POSTing 30 KB of junk to a public unauthenticated production endpoint). To demonstrate a bug on a deployed service, propose the exact request and **ask**; do not send it.
> - **Subagent claim contract.** Instruct every subagent you dispatch to tag each claim it returns as either `[verified: <path:line | command output | URL>]` or `[inferred]` — and hold yourself to the same tagging. An `[inferred]` claim is **never** relayed to the user as fact and **never** acted on until you have verified it yourself. Implementer subagents must show the red run; a gate that ran 0 tests is not green; prove absence only with an exit-checked command (no `|| echo`, `head` or grep-pipe hiding the result).
> - **You own your workspace exclusively while any gate, review or verification runs.** Never let a second agent work in it concurrently — concurrent subagents sharing one jj workspace manufactured two false-positive diagnoses, one of which was nearly shipped as a fix. Run gates yourself, or one subagent at a time, and point every reviewer or verification subagent at a **fixed revision** (a jj change id — `jj diff -r <change-id>` — or a git commit sha), **never** at live `@`, which moves under them mid-read.
> - **On a timeout on your question tool (the user is AFK): continue, but park.** Carry on with internal work that is safe and reversible — reading, analysis, drafting inside your own workspace — and take **no outward-facing action** while the question is unanswered: no assigning reviewers, no Slack messages, no board writes, no publishing, no sending. (A timeout once led to a reviewer being assigned unasked, and then kept.) Record the pending question in the Result section of this note and put it to the user again when they return.
> - **Production-secret reads are the human's to run — plan for that up front.** `kubectl get secret`, `op …`, or any `curl` carrying a live token is handed to the user to execute. Say so in your **first** proposed action list rather than discovering it mid-diagnosis, and design the plan around an explicit hand-off point: you prepare the exact command, they run it and paste back only what is needed. Never print or persist a secret value.
> - **Code tasks — step 0, create your own workspace before any other work** (immediately after the premise check). The session starts in the project directory (`project_dir`, an already-trusted checkout). As your first *work* action, create your isolated workspace rooted on trunk, then `cd` into it (your Bash cwd persists between calls). Emit **only** the block matching the detected `vcs` — never both, and never a guessed one:
>   ```bash
>   # vcs: jj
>   jj -R <project_dir> workspace add --revision main --name <slug> ~/projects/jj-workspaces/<slug>
>   cd ~/projects/jj-workspaces/<slug>
>   ```
>   ```bash
>   # vcs: git
>   git -C <project_dir> fetch origin
>   git -C <project_dir> worktree add -b <slug> ~/projects/jj-workspaces/<slug> origin/main
>   cd ~/projects/jj-workspaces/<slug>
>   ```
>   (The `~/projects/jj-workspaces/<slug>` path is the convention for both — adjust if needed.) Rooting on trunk (`--revision main` / `origin/main`) is load-bearing: without it the workspace inherits whatever `@`/`HEAD` points at (often a stale WIP), and the first code-map runs against stale code. Do **all** subsequent TDD/code work from inside this workspace, keeping every edit within it. If the actual workspace path differs from the frontmatter, record it in this note's `jj_workspace` field. Premise-check step 0 still applies to you and every scout subagent: read trunk at origin, not the on-disk `@`, or you will produce confidently-wrong "that code doesn't exist" findings.
> - **Code tasks:** do red-green TDD; use subagents wherever possible; tier subagent models by difficulty (opus / sonnet / haiku: cheap/mechanical work on lower tiers, judgement-heavy work on the top tier). Edit inside the jj workspace.
> - **Non-code tasks:** gather relevant context (who/what, from meeting notes / Slack), then prompt the user with the concise action, drafting the message or artefact where useful so they just review and send.
> - **On finishing — this differs for code vs non-code:**
>   - **Non-code:** when the outcome/artefact is complete, set `status: done` and write the outcome into the Result section of this note (what shipped or was decided, artefact reference, key decisions, gotchas, optional `⚡ worth a knowledge note: …` flags). A non-code task has nothing to merge, so `done` is the right terminal state.
>   - **Code:** opening a PR is **not** "done" — the user merges it later, never you. The finishing sequence, in order: (1) work complete and gates green (the repo's lint/type/test commands) → (2) **push your `<slug>` bookmark/branch and open a PR with the repo's own tooling** — follow its AGENTS.md/CLAUDE.md or its own PR skill/workflow if it has one (e.g. agent-pawl's `/pawl` review-pr), else `gh pr create` for a GitHub repo → (3) **wait for CI to go green via the forge** (`gh pr checks --watch`, in the background is fine); on a failure fix it and push again — never hand over while checks are running or red → (4) **stop: the user merges.** Then set `status: blocked` with `blocker: awaiting review/merge of <PR link(s)>`, and write the PR link(s), key decisions, gotchas and optional `⚡ worth a knowledge note: …` flags into the Result section of this note. Do **not** set `status: done` for code — the task is closed to `[x]` later, once the PR is actually merged (via the brain-collect skill).
>   - In **both** cases, as part of normal finishing: do **not** *spontaneously* run a full persist, and **never** write top-of-mind, private.md or knowledge notes yourself — your Result section is the handoff (a coordinator's own workers' Today lines, above, are the one exception). **BUT** you MAY run the brain-persist skill in worker mode to checkpoint your journey mid-session — a **scoped** persist (session note + knowledge notes + re-index, **never** top-of-mind or private.md, **never** the diary). And on collection, the main session will trigger the brain-persist skill in worker mode **in this very session** before teardown, so your journey/decisions/friction get captured from full context (it sets `collect_state: collecting` in your worker note as the trigger; your scoped persist flips it to `persisted` as the completion signal).
> - **On being blocked mid-work (a different, external reason):** if you have done everything you can but **cannot reach the goal because you are waiting on an external event** (a person's reply, a deploy, a decision — not merely a PR you just opened), set `status: blocked`, add a `blocker:` field describing what/who you are waiting on, write your findings-so-far into the Result section of this note, and **stop** — do not spin, and do not invent other status values. So `blocked` covers **both** "stuck mid-work on an external dependency" **and** (for code) "work complete, PR up, awaiting review/merge" — the two are distinguished by the `blocker` text.
>
> **6. Wait for the brief to land on the host.** Run `bash ~/projects/brain/skills/brain-dispatch/scripts/wait-for-brief.sh --host <host> --slug <slug> --note-dir <workers|private/workers>`; it prints `synced=yes|no`. A remote worker reads the note from that host's synced copy of the vault, which lands seconds after your write, so launching first hands the worker a missing file as its very first action; on this machine the answer is immediate. On `synced=no` (rc 1): **stop**, leave the note at `status: primed`, and report.
>
> **7. Launch and verify.** Run `bash ~/projects/brain/skills/brain-dispatch/scripts/launch-worker.sh --host <host> --harness <harness> --slug <slug> --project-dir <project_dir> --note-dir <workers|private/workers> --scope <shared|private|all> --project <project>`, adding `--model <model>` only when a model is set (given in the request, or re-used from the note on a resume, step 0); it prints one line, e.g. `verified=yes|no session=brain-worker-<slug> rc=yes|no|n/a attach=<attach command> session_id=<id|unknown> mode=launch|resume`. `attach` itself contains spaces, so parse fields **by key from the right** (`session_id=` and `mode=` are the last two, appended after `attach`). The script types the launch line and checks the typed line arrived intact before committing to it, because a shell still initialising — or an interactive prompt fired by the project directory — has silently eaten the first characters of the command. It then polls the pane until the harness's **own** chrome is up — its composer free, or already running the priming turn the brief started — because "session created" is not "agent ready" and the typed command line itself reads as a false ready. Do not re-implement either check, and do not describe the launch keystrokes here — they live in the script. Once the composer is verified up, and only then, the script also connects the worker to **Remote Control** under its own `<slug>` when the harness supports Remote Control (`rc=yes`); a harness without it reports `rc=n/a`, and a connect that could not be confirmed reports `rc=no`. Remote Control is a **convenience, not a launch gate**: `rc=no` never changes `verified` or the exit code.
> - **On `verified=yes` (rc 0):** set the worker note `status: working`, correct the note's `attach` field if the script's value differs from what you wrote, and record the script's `session_id=` value in the note's `session_id:` frontmatter field (`unknown` if that's what the script reported).
> - **On `verified=no` (rc 1):** leave the worker note at `status: primed` and report. Do not pretend it launched; the session is left running for inspection. A resume whose tmux session is still alive also returns `verified=no`, with nothing sent to the pane — attach to it or kill it first.
>
> **Return only this concise summary** (nothing verbose — no qmd dump, no note body, no pane text):
> - `slug`, `task_type`, detected `vcs`, resolved `project_dir`, `host`, `harness`, session name (`brain-worker-<slug>`), the `attach` command, `verified` (yes/no), `rc` (yes/no/n-a — Remote Control), worker-note path, `area`, `project` (and whether you added a registry row), and the **exact Today action text** to flip. Add a one-line **low-disk warning** if free space was under ~20 GB, and a one-line **guardrail warning** if the preflight reported `guardrail=inactive`.
> - **On failure** (preflight refusal, directory missing, harness binary missing, free disk under ~5 GB for a code worker, brief never synced, or startup never verified): the reason, and that the action was **not** launched.

## Step 3 — flip the Today action and tell the user (main session)

The main session is the sole writer of top-of-mind and private.md (a coordinator worker dispatching its own workers counts as their main session for their top-of-mind Today lines only — see the priming's coordinator exception; it never dispatches a private-area worker, but asks the user's main session to), so it performs this final step itself using the launcher subagent's summary:

- **On verified success:** flip the matching Today action to `[/]` in `$(brain-scope today-file <area>)` (`00-home/top-of-mind.md` for `work`/`projects`, `private/private.md` for `private`), appending the suffix `— dispatched worker brain-worker-<slug>`. Then report **one line** to the user with the host, harness and attach command:

  > Dispatched `<slug>` on `<host>` (`<harness>`) — attach with `<attach>`.

  When the launcher summary reported `rc=yes` — the harness supports Remote Control and the worker connected — extend that same line with the steering clause:

  > Dispatched `<slug>` on `<host>` (`<harness>`) — attach with `<attach>`, or steer it remotely as `<slug>` (Remote Control).

  On `rc=no` keep the plain line and add a brief note that Remote Control did not connect (the worker is running and still attachable with `<attach>`). On `rc=n/a` say nothing about Remote Control — that harness has none. A trailing `rc_dialog=dismissed` means Remote Control's 'already connected' dialog was open and the launcher closed it with Escape; `rc_dialog=stuck` means it is still open — attach and pick Continue, never Disconnect.

- **On failure** (the subagent reported a preflight refusal, a missing directory, a disk-preflight refusal, an unsynced brief, or an unverified startup): report the failure to the user and do **NOT** flip the Today action.
